# 大肥鱼原生工具 Agent（0.7.6）

大肥鱼继续使用 AstrBot 的同一个 `ToolLoopAgentRunner`。llama.cpp 负责将 Qwen
输出解析为协议正文与 `tool_calls`，AstrBot 负责工具执行、工具结果消息、模型回退和
上下文压缩。插件通过公开的 `FunctionTool` / `Context.add_llm_tools()` 注册工具。

当前固定版本没有公开的“否决结束并继续”接口，因此 `on_agent_begin` 为当前 Runner
实例绑定生命周期适配器；不修改 AstrBot 上游文件、共享 Provider 或全局 Runner 类。
升级 AstrBot 前必须运行原生 Runner 集成测试，核对这四个实例方法仍然兼容。

## 执行与结束

每一步先核对会话版本、用户中断和全局预算，再校验工具参数与权限。有工具调用时
执行工具并回填明确结果，继续同一个 Runner；工具步骤中的正文不发送给 QQ。
完整且没有工具调用的三字段候选才进入语义检查：

```json
{"reply":"聊天正文","thinking_level":1,"voice":false}
```

语义检查最多三次，第一次即计数；前两次可要求内部续跑，第三次仍要求继续则进入
一次工具禁用的受限收尾。超时和非法判定同样消耗检查次数。工具调用、重新生成、
Provider 回退和上下文替换都不会重置次数。内部续跑使用系统消息，不伪造用户输入
或启动第二个前台 Agent；旧的私聊可选补发流程已删除。

默认全局限制是 16 次模型请求（含检查与收尾）、16 次工具调用、180 秒。
`agent_max_requests`、`agent_max_tools`、`agent_max_seconds` 可以在插件配置中调整；
语义检查上限固定为 3。另保留 AstrBot 原生步数限制，适配器提前收尾以免触发原生
强制补写的用户消息。检查请求单次最多 25 秒，收尾最多 30 秒，均受剩余总时间约束。
检查/收尾使用 JSON Schema，并给开启思考的 Qwen 留出足够输出预算。

0.7.6 为固定 AstrBot Provider 补齐单次请求参数：通过独立请求副本的
`custom_extra_body` 传递 `response_format`、输出预算和思考参数，不修改共享
Provider、客户端或上游源码。检查与收尾的 JSON Schema 会实际到达 llama.cpp。
有可用工具的主请求继续使用原生 tool-choice；当前 llama.cpp 的正文 JSON Schema
会覆盖工具语法，因此不向这类主请求附加正文 schema，候选仍由本地严格校验。
普通正文或字段格式不合法时，下一次内部格式修复暂时禁用工具并附加候选 JSON Schema；
得到合法候选后恢复正常工具决策，语义检查仍可要求补做实际动作。
同一运行累计 3 个无效候选，或同一无效输出重复 2 次，就提前进入受限收尾；
不消耗或重置语义检查次数，不再为重复格式错误耗完 16 次全局预算。
内部续跑不回填被拒绝的助手正文，只保留最新修正指令和真实工具调用/结果；
收尾仅接收真实对话和当前动作/发送回执。
结束检查还显式接收本次链接/音频是否实际发出、已受理歌曲等待前台释放的状态；
后台尚未合成或尚未发送候选不能成为重复续跑的理由，错误的已发送陈述仍需修正。
普通 voice=true 在批准后由程序自动合成，emotion 仅用于指定情绪，不是必做步骤。

当前模型上下文为 32768 token，K/V 缓存均为 Q8_0。`configs/runtime/qwen3.yaml`
统一维护上下文、KV 类型、输出上限、思考预算和输入余量；启动脚本、模型探针和 AstrBot
provider 配置生成器共同读取此文件。修改后重启服务，启动流程会同步生成 AstrBot 配置。
AstrBot provider 同步配置该上限，并启用原生上下文
管理。默认轮次压缩器使用完整 user 轮次作为边界，保留最新用户请求及其全部
工具调用/结果对。每次模型请求前通过本机 llama.cpp 的 `/apply-template` 和
`/tokenize` 计算包含工具 schema 的实际输入，按 provider 从共享配置带入的参数预留
输出 token 和余量；当前分别为 1536 和 256，实际输入预算为 30976 token。
历史过长时继续移除最旧完整轮次；最新一轮仍超限或分词失败时受限结束，不发送
已知超限请求，不向 QQ 泄露底层异常，也不重复执行工具。分词不生成模型回复，
不消耗语义检查次数，但受任务总时限和会话版本保护。

搜索每页只请求 10 首，传给模型的列为候选序号、歌名、歌手、别名、时长、可用性和链接，
使用 `song_columns` 与 `songs` 行数组。歌曲 ID、专辑和授权凭据留在程序和完整审计中；
候选序号在当前任务内稳定，翻页和重复查询不会将旧序号指向另一首歌。语义检查读取实际动作
回执和候选数量，避免再次携带完整候选列表；只有最近一次内部修正指令继续
进入模型上下文，完整生成历史仍在独立审计中。压缩不重置执行和检查预算。

每次主请求都更新当前任务的候选序号和查询状态，防止沿用旧聊天中的序号。
执行前拒绝记录在独立审计中并进入结束检查，但不预占动作键；后续补齐检索后
可以正常执行同一候选。结束检查的回复对象使用 `draft_reply`，与选歌参数
`candidate` 区分；检查同时读取最近 10 首的精简元数据和拒绝是否已解决的事实，
不把“未登记候选”或“尚未检索”误报成“没有音源”。内部状态不写入已发送聊天历史。
同一个结束检查还提取候选是否声称本轮歌曲开始准备、歌曲完成、链接已发、音频已发；程序用真实回执
核对四项布尔陈述，不能让 `finish` 覆盖没有证据的准备/完成/发送陈述。这不新增模型请求，
检查仍关闭思考，三次上限和全局预算不变。受限收尾保留人格，输入仅包含本轮请求
和回执，避免旧聊天的失败描述覆盖本轮成功受理。

模型将工具请求误写为正文 `name/arguments` JSON 时，正文参数不会执行。若名称属于
当前已注册工具，下一次请求通过临时 `tool_choice` 限定该工具，让模型按原生 schema
重新生成真实调用；执行后恢复自动选择，仍受原有预算、权限和幂等约束。未注册工具
不进入此修复路径。2026-10-29 的两条实际《雨爱》请求分别暴露了无任务却声称准备中，
以及正文工具请求重复后收尾的问题；两次都没有创建任务，也没有进入下载阶段。
0.8.1 的 63 项生命周期、请求传输及上下文测试通过。使用运行中的真实 Qwen 回放
此次失败消息及候选未登记恢复场景，均完成 `weapi → musiccover`，任务只受理一次；
原始无任务的准备中草稿也能被检查器拒绝。回放媒体为模拟回执，没有发送 QQ 消息，
没有生成真实翻唱成品。

## 工具

| 工具 | 输入 | 明确结果 |
|---|---|---|
| `emotion` | `text`、`emotion` | 合成语音并返回 `prepared` 凭据；不直接发送。最终 `reply` 对应文本、`voice=true` 时复用音频 |
| `weapi` | `action=search` + `query`/`page`，或 `action=resolve` + `candidate`；用户直接提供 ID 时可用 `song_id` | 返回候选元数据、页面链接或当前账户可获取的音频链接；不播放 |
| `musiccover` | `action=start/replace` + 本轮 weapi 的 `candidate`；或 `action=cancel` | 受理本人翻唱、改点或取消自己的翻唱任务，返回明确回执 |
| `music` | 同上 | 受理原唱播放、改点或取消自己的原唱任务，返回明确回执 |
| `sticker` | 枚举 `tag` | 发送现有表情；返回 `sent`、冷却跳过或素材不可用 |

工具描述和参数说明全部在 `configs/qq_companion/prompts.yaml`。参数类型、枚举、
权限及执行条件由代码校验。不会让模型传任意文件路径或指定其他 QQ 收件人。
原有 `q2_echo` 仅保留为本地协议诊断工具。

歌曲候选由前台 Agent 自己选择。weapi 在后端保存绑定会话的候选凭据，模型只需
传 `candidate`，程序映射真实 ID 并携带凭据复用查询结果；后台不再重新搜索、获取歌曲元数据或
调用另一个选歌模型。下载时仍会取得有效的临时音频地址。凭据过期或跨会话使用会拒绝提交。
新任务原子地保存具体选择并进入 `awaiting_commit`；当轮前台释放后才
`commit` 为 `waiting_gpu`。这避免翻唱提前卸载 Qwen，与尚未结束的 Agent 相互等待。
提交和 commit 都幂等；恢复时不会把已选歌曲退回搜索。
若指定音源已确认 `available=false`，`musiccover` 直接返回 `unavailable` 和已查到的
歌曲信息，不创建任务、不承诺正在翻唱，也不擅自改成其他版本。

思考开关按请求阶段设置，由共享 `qwen3.yaml` 生成 provider 配置。主 Agent、工具规划、
内部续跑和选歌开启；格式修复、语义检查、受限收尾、歌曲结果/澄清通知和摘要关闭。
关闭时同时传 `enable_thinking=false`、`reasoning_budget_tokens=0`；不增设开关分类模型。
`temperature/top_p/top_k` 同时接入 llama.cpp 启动参数和 AstrBot 请求；检查、修复和摘要
使用 `utility_temperature=0`，结果通知和收尾使用 `result_temperature=0.5`。
原生摘要通过同一个请求适配层，计入当前 Agent 请求预算并受总时限、插话保护；
摘要请求不携带聊天 JSON 指令，摘要后保留原人格系统消息。受限收尾也保留人格。
旧 few-shot 仍描述爱莉希雅，与大肥鱼人格冲突，故共享配置明确设为 0；启动同步清空
AstrBot 的 begin_dialogs。日后若配置兼容示例，启动同步会将其转成当前三字段传输格式。

历史对比（20 首改为 5 首时）：《雨爱》冻结同一批候选、用活动 Qwen 分词器测量：结果体 20 首 1283 token，
5 首且移除 ID/专辑后 268 token，减少 1015（79.1%）。同一固定上下文、同一旧工具 schema
的完整续跑请求为 4985 → 3970，减少 20.4%；这是隔离搜索结果变化的对比，
采用最终提示词和新工具 schema 后为 4105 token，较修改前减少 880（17.7%），
并非任意真实聊天的总 token。原始结果和计数保存在 ignored storage 的
`rain-love-token-baseline-20261029.json`，可用 `benchmark_song_tokens.py after` 复核。

`agent_budget_reply` 的固定正文保持不变。第三次检查要求继续时先尝试一次受限收尾；
请求次数、工具次数或总时长不足以继续时也进入收尾。只有无法再请求模型，或收尾请求
失败、超时、返回非法格式时，才发送这句固定正文。GPU 准入等待也受总时长限制，
等不到可用模型时直接使用该正文；用户已经插话时不发送旧任务的收尾。

## 中断、幂等和历史

私聊和明确发给机器人的群聊请求在异步查询群信息/转写前推进前台会话版本，旧
Runner 立即停止。普通群聊仍进入该群近期上下文，但不推进前台版本、不取消歌曲；
是否开启回复仍遵守 @、引用、唤醒词和自动接话规则。自动接话不暂停后台点歌。

检查结束、准备执行工具、每次发送以及 OneBot 实际分发前都校验版本。
OneBot 校验发生在图片/语音异步编码之后；已经提交到传输端的发送无法撤回。
后台音乐通过 `song_tasks.sqlite3` 保存独立任务状态、请求者、模式、任务版本和
音频/完成回复各自的发送回执。已受理任务不会因前台草稿失效或其他群成员的新请求
而取消。请求者向机器人发来新请求时，先暂停本人旧任务交付，由同一个前台 Agent
决定是否调用 `action=cancel/replace`；正常对话处理完即解除暂停。群聊中取消和改点
需要按现有方式 @、引用或唤醒机器人；私聊直接发送即可，不用另造内部用户消息。
取消只作用于当前请求者在当前会话的同类任务；改点在新曲确认受理后才撤销本人旧
点歌，新曲不可用或提交失败不会撤销旧曲。管理员修改群开关/静默设置会使旧任务
失效；其他群和私聊不受影响。最终校验发生在异步音频编码之后，暂停会等候新请求
处理结束，明确取消会拦截后续发送。已成功发送的音频不会因回复暂停或恢复被重发，
传输结果不确定时冻结交付，不自动重复。旧版已取消任务不会在升级时复活。

插件启动恢复时清除旧前台流程遗留的临时暂停，保留任务状态和各段发送回执。
新歌提交期间若前台已被新请求替代，已受理的新歌仍可恢复，但旧流程不能继续执行改点取消动作。

0.8.0 在点歌受理时通过有作用域的候选凭据冻结本次搜索池。音源准备先在 CPU 上
实际下载并用 ffprobe 校验完整音频，再卸载聊天模型进入翻唱；遇到 HTTP 403 则把
对应歌曲 ID 持久记为淘汰，进入 awaiting_reselection。Qwen 的 selection 阶段只接收
剩余候选，选中后沿用原任务、原唱/翻唱模式和用户请求，不再创建前台 Agent 或发送准备消息。
同名、同歌手且时长相近的候选仍存在时，用 JSON schema 约束模型必须继续选，避免
过早放弃。候选序号保留间隙；淘汰条目不传给模型，也无法通过接口重新选回。
每次重选最多三次模型请求，非法输出和超时均计入持久预算；每次淘汰推进重选版本，
旧版本提交、取消后的提交和跨会话提交会被拒绝。服务重启保留候选池、淘汰名单和预算。
下载成功后校验文件哈希并复用，后续 worker 不重复下载。候选全失败则标记
source_candidates_exhausted；剩余条目均不符合用户指定作品/版本时，允许明确结束为
no_suitable_remaining_candidate，不能换成无关歌曲。结果通知送达与任务成功独立记录，
失败不会因为发出了链接或失败说明而变成成功。新机制不自动重启历史失败任务。

`storage/qq_companion/agent.sqlite3` 保存独立审计：`generated`、`semantic_check`、
`approved`、`sent`、工具结果、失败与任务状态。相同 run 内的同一工具/参数只执行
一次，后续调用复用回执。执行中断、网络超时或发送结果不确定时不自动重做动作。

AstrBot 的日常聊天历史只保留真实输入与已确认发送的内容。内部工具消息、检查结果
和未发送草稿仅参与当前运行，并在审计库单独记录；分段发送中途失败时只记录已发送
部分。后台音频、链接和回话也分别记录实际发送，避免把部分成功写成全部成功。

0.7.1 在读取旧聊天时剔除遗留的 `think` / reasoning 块，保留实际聊天正文。
0.7.6 同时移除助手历史中的方括号发送回执和旧控制标签，保留真实回话及用户原文；
兼容旧版把消息组件存成 JSON 字符串的记录。后台歌曲只把实际发出的回话写入聊天，
音频交付事实继续保存在独立任务/发送审计中。
结束检查只接收真实对话、本次请求、当前工具能力和本次已解析回执；不把内部草稿、
人格指令或历史成功描述当成本次执行证据。控制标签和程序发送回执不允许进入候选或
语音合成。语音准备与发送分别审计，并记录对应文本和本地音频路径。

语音回复按消息内容混合交付：自然句子生成语音，颜文字和表情符号保留为文字消息，
不会先把颜文字规范化成数字再合成。自动合成和 emotion 提前准备的音频均遵守此规则；
已发送审计分别记录实际朗读的文本与实际发出的颜文字，内部草稿仍单独保留。
结束检查显式读取本次 sent_this_run 回执，内部查到链接和 queued 状态不代表用户已收到。

## 验证与安装

原生集成测试使用 `envs/astrbot/Scripts/python.exe`；该环境的 Python 3.12 与固定
AstrBot 匹配。开发环境的 pytest 在 `.venv/Lib/site-packages`，可追加到模块搜索路径
后运行 `tests/test_qq_agent.py` 及其他 QQ 测试。Python 3.10 下该原生集成文件明确跳过。

```powershell
envs/astrbot/Scripts/python.exe scripts/qq_companion/probe_agent_native.py
```

模型栈已运行时可用 `--existing --replay`，通过 GPU 准入租约复用本机 8080 模型。
`--existing --recent-failures` 回放最近两次耗尽 16 次请求且未进入语义检查的请求，
读取各自之前的真实聊天历史，核对原生搜歌/翻唱受理与重复动作、虚构发送陈述。
该回放读取当前聊天的文本上下文，主动注入一次无工具依据的完成声明，检查真实
Qwen 是否拒绝该候选并继续调用工具。媒体仍全部模拟，不发送 QQ、不重启模型。
回放同时包含当前会话历史与实际 20 条搜索结果，核对可继续选择正确歌曲并调用
翻唱工具；这不等于已完成真实翻唱或 QQ 成品交付。

真实模型探针独占 GPU Broker，在 `127.0.0.1:18080` 临时启动当前 Qwen，使用真实
AstrBot Provider、Runner、工具执行器和结束检查；媒体结果模拟，不连接 QQ、不调用
真实网易云或翻唱。结束后关闭自己启动的进程，报告在
