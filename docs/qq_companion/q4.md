# Q4 语音、点歌、整首翻唱与表情

插件 `0.6.0` 使用 AstrBot 的同一个角色 Agent，在同一次主回复中输出媒体决策。程序不按聊天关键词判断唱歌意图。本次验收不连接 QQ。

## 行为与提示词

- 角色提示词明确指定语音触发时优先遵守，没有明确要求再结合情绪；未触发时采用语音输入回语音、文字输入回文字的默认方式。
- AI 明确判断用户要求由角色唱歌才翻唱，否则播放原唱；歌曲或意图不清楚时自然追问，不展示搜索、版本或音色选择菜单。
- 翻唱固定从头处理整首。模型提取纯作品名，不把副歌、时长等条件混进歌名。
- Qwen 开启真实思考模式，启动参数为 `--reasoning on --reasoning-format deepseek --reasoning-budget 1024`，AstrBot 模型配置同时传 `enable_thinking=true`。推理内容与正文分离，不展示给 QQ；`thinking_level` 仍只是发送节奏档位。
- 搜索后由同一个 AstrBot Provider 再思考一次：保留用户原话及当前会话的有界上下文，结合候选的歌名、歌手、专辑、别名／副标题选择 ID，不由程序按关键词或标题精确匹配选歌。无结果或没有合适版本时，AI 自然询问准确名称，不给例子、列表或菜单。
- 演唱前只引导模型以角色口吻回应并表达准备需要时间，不提供示例句。先发送这句回复，再创建后台任务；完成后等待模型恢复并通过就绪检查，由同一模型生成有效回话后，向原会话连续发送成品和回话。恢复失败时保持等待，不提前发送成品或套用成功文案。结果回话生成或解析失败时最多调用三次，间隔 1、2 秒；仍失败则保留 `pending`，下次插件启动恢复，不使用固定成功文案，不重复合成歌曲。歌曲任务失败时由模型如实说明。
- AI 可按情绪低频发表情，每个会话至少间隔 60 秒，并受群启停、静默规则约束。

`configs/qq_companion/prompts.yaml` 的 `media_decisions`、`music_selection`、`music_clarification` 和 `music_result` 可直接编辑，每次请求重新读取；角色人格位置保持不变。内部选歌仅使用选歌任务提示词，可见回话仍结合完整角色人格。主回复结构示例：

```json
{"reply":"模型结合当前对话生成的准备回复","thinking_level":2,"voice":false,"emotion":"gentle","music":{"mode":"cover","query":"雨爱","artist":""},"sticker":null}
```

无动作时 `music`/`sticker` 为 `null`，`voice` 必须为布尔值。代码生成角色 ID、文件路径、任务 ID、URL 和收件人；模型不能指定任意路径或另一个 QQ 收件人。非法结构不触发媒体动作。

## 运行与限制

正常 `scripts/qq_companion/start_all.ps1` 默认启动 Qwen3、ASR、GPT-SoVITS、wrapper 和媒体 API，再启动 QQ 组件。`-WithoutTTS` 显式降级文字，旧 `-WithTTS` 参数仍兼容；`-NoModels` 保留 Q1 诊断用途。

输入语音只从可信 OneBot `get_record` 结果读取，经 FFmpeg 转单声道 16 kHz WAV，限制 12 MiB、60 秒。输出为单声道 24 kHz WAV。TTS 按段串行，失败段回退文字；群聊超过 180 字、私聊超过 1500 字时使用文字。主回复最多发三条群消息、六条私聊消息。

歌曲使用 weapi 对当前账号正常提供的音源，拒绝试听、无地址、未知下载域名、跳转和实际时长不完整的文件，不提供 VIP 绕过。每次检索先取前 20 条并保存元数据，AI 依用户原话选择具体版本；指定版本不可获取时不擅自换版，按已有规则提供该曲链接。可选 Cookie 从 `ASTRBOT_CHAT_NETEASE_COOKIE` 读取，兼容 `ALYSIA_NETEASE_COOKIE`，不传给音频 CDN。

状态流程为 `queued → searching → awaiting_selection → waiting_gpu → running → completed`。无候选或 AI 选择 `null` 时进入终态 `needs_clarification`，释放队列名额，通过专用提示词生成追问；搜索接口故障仍走 `failed`，不伪装成用户歌名错误。插件通过带认证的 `POST /v1/songs/{id}/select?scope=…` 提交模型选中的 ID，后端只接受已保存候选里的整数 ID 或 `null`。在选择之前不下载或切换 GPU，重启恢复保留候选和已选歌曲。

`songs.sqlite3` 保存 `user_request`、`request_context`、`search_results`、`selection`。上下文只来自同一会话的短窗口，最多八条并进一步限制字节数。选歌生成或格式错误最多三次（1、2 秒退避），耗尽后保留待处理交付，不套用默认歌曲。`media_state.sqlite3` 的 `song_selection_attempts` 记录最终 JSON、ID、错误类型和推理字符数，不保存思考正文。旧数据库自动补齐字段和表，已有任务保持不变。

后台搜歌每个任务最多尝试三次（首次加两次重试），失败后分别等待 1、2 秒。仅超时、连接/响应中断、HTTP 或接口业务码 429/500/502/503/504 重试；找不到匹配、试听/不可用、认证/权限失败、跳转、证书或返回格式错误不重试。每次尝试在网络请求前持久化计数，历史记录保存安全错误码，重启不重置已用次数。已选好歌曲的合成恢复复用原选择，由下载阶段重新核查播放地址。该策略不会重试整首合成或重复发送，也不会自动翻页、改写歌名或替换歌曲。达到上限后向用户自然说明失败，不展示技术错误码。

任务状态 API 返回 `search_attempts`、`search_error`、`search_history`、`search_results` 和 `selection`；历史 `error` 为空表示该次成功，`in_progress` 表示未完成，其余为错误码。

`storage/qq_companion/songs.sqlite3` 保存任务，最多三项等待/进行中，单首最多 600 秒、源文件最多 30 MiB。一次一个歌曲 worker。原唱只下载转码，翻唱执行整首分轨、Feiyu RVC、混音，并校验模型哈希、回执和时长。

翻唱沿用主管持有的全局 GPU Broker。冻结新 GPU 请求，等待活动租约和真实 llama-server slots 排空，再停止受管模型、核查进程和至少 12288 MiB 可用显存。成功、失败和取消均先回收 worker，再恢复原模型，检查健康状态、Qwen 实际生成与 TTS 实际合成。恢复失败进入 `recovering`，不开放新请求，不抢占训练。

发送使用原始 OneBot 会话，历史仍使用 Q3 的规范 ID。群设置变化会取消旧结果。发送前持久化 `sending`，结果不明或发送期间崩溃标记 `uncertain`，不自动重发；未开始发送的任务可重启恢复。结果经 AstrBot 同一会话锁写入其历史，不建立第二套聊天历史。

`media_state.sqlite3` 的 `song_reply_attempts` 表记录任务号、尝试次数、原始模型输出（最多 2000 字）、解析后的回话及安全错误类型。`generated` 表示有效模型回话，`rejected` 表示格式无效或调用异常；结合 `delivery` 状态核对是否实际发送。记录不包含人格提示词或访问令牌。格式要求在当前用户任务中再次明确，区分角色正文与程序 JSON 传输结构，避免人格中的自然聊天/表情标签规则覆盖结果格式。

素材库为 `storage/qq_companion/stickers`，初始化器提供五种自行绘制的 CC0 几何表情，可替换为同名授权素材。缓存每小时扫描，清除超过 24 小时的终态歌曲及临时发送音频。图片/GIF/视频理解仍待 Q7，Q4 不把图片交给文本模型。

已核对 [matsuko_cover](https://github.com/sdfsfsk/matsuko_cover) 的默认菜单流程，与本次交互要求不同。本阶段将项目已有 weapi 和 Feiyu 实现迁入 `services/media_api`，由当前插件统一控制交互。

## 本地验收

```powershell
envs/astrbot/Scripts/python.exe scripts/qq_companion/probe_q4_local.py
envs/astrbot/Scripts/python.exe scripts/qq_companion/probe_q4_result.py
envs/astrbot/Scripts/python.exe scripts/qq_companion/probe_q4_selection.py
runtime_env/python.exe -m pytest tests/test_qq_q4.py -q --basetemp storage/temporary/pytest_q4
runtime_env/python.exe scripts/qq_companion/probe_q4_source.py
runtime_env/python.exe scripts/qq_companion/search_music.py
runtime_env/python.exe scripts/qq_companion/probe_q4_audio.py
runtime_env/python.exe scripts/qq_companion/probe_q4_model.py
runtime_env/python.exe scripts/qq_companion/supervisor.py --local-q4-acceptance
```

分别检查真实 AstrBot 类与模拟收发、契约/故障、真实 weapi、三首真实整首合成、真实 Qwen 意图，以及生产停启/语音 API。均不启动 QQ 组件。GPU 探针持有全局锁，结束按 PID/启动时间关闭自己创建的进程树，不能并行运行。结果见 `acceptance.md`；本地通过不代表真实 QQ 客户端播放已验证。

`probe_q4_result.py` 单独使用已运行且就绪的 Qwen，以活动租约避免翻唱卸载；通过锁定版本的真实 `Context.llm_generate`/Provider 检查五次结果回话，记录到忽略目录 `storage/temporary/q4-result-acceptance`，不会创建或发送 QQ 消息。

`probe_q4_selection.py` 用请求级思考设置检查真实选歌、意图和追问，原始候选取自 `search_music.py` 保存的 weapi 结果；不加载第二份模型、不发送 QQ。`search_music.py` 只查雨爱、奇迹再现、年轮、叹云兮，每首前 20 条，输出含副标题的表格及 JSON 到 `storage/temporary/song-search-results`，不下载音频。原 `select_song` 精确匹配辅助函数仅保留给旧的独立音源验收，不再用于生产选歌。

遗留服务可先用 `runtime_env/python.exe scripts/qq_companion/cleanup_orphans.py` 检查。只报告主管已退出且同组存在 AstrBot/媒体 API 的伴随服务；加 `--apply` 才清理。独立后台聊天、活跃主管、训练和 NTQQ 均排除。
